## 引言：当博客突然消失

![引言：当博客突然消失](/images/illustrations/2026-02-22-github-pages-404故障排查深度分析与根因定位-01.png)


2026年2月22日中午，一个紧急问题打破了平静的工作日。我的技术博客 `https://s-ai-unix.github.io/` 突然显示 404 错误，所有文章和页面都无法访问。

**上午还是好好的，为什么中午就挂了？**

这个问题引发了连锁反应：我刚刚写好的几篇数学物理文章（包括希尔伯特作用量、比安基恒等式等）可能丢失了。更令人困惑的是，我没有对博客做任何特殊操作，只是正常提交了几篇文章。

这场故障的排查过程，不仅揭示了 GitHub Pages 部署的复杂性，更展现了两种不同问题解决方法的本质差异——以及为什么**深度分析**往往比**表面观察**更有效。

## 第一章：问题的初步诊断

![第一章：问题的初步诊断](/images/illustrations/2026-02-22-github-pages-404故障排查深度分析与根因定位-02.png)


### 1.1 症状描述

访问 `https://s-ai-unix.github.io/` 时，浏览器显示：

```
404 Not Found
```

**关键时间点**：
- 上午 12:00 前：博客正常访问
- 中午 12:00 后：开始出现 404 错误
- 怀疑原因：`.gitignore` 文件修改导致文章丢失

### 1.2 初步检查

首先检查最明显的问题——文章是否还在仓库中：

```bash
git ls-files | grep "2026-02-22"
```

> **Git 仓库（Repository）**：版本控制系统，记录项目所有文件的历史变更。可以想象成一个时光机，能让你回溯到任何历史时刻。

结果令人欣慰又困惑：

```
content/posts/2026-02-22-希尔伯特作用量.md
content/posts/2026-02-22-比安基恒等式.md
content/posts/2026-02-22-黎曼猜想从素数分布到复平面的零点之舞.md
```

**文章都在！** 这说明问题不是文章丢失，而是别的地方出了问题。

### 1.3 第一条错误路径：表面分析

#### GitHub Actions 失败日志

查看 GitHub Actions 的运行记录，发现：

```yaml
Run #333 (UTC 2026-02-22 05:15:32Z)
Status: failed
Error: Failed to create deployment (status: 404)
Ensure GitHub Pages has been enabled
```

这个日志似乎指向一个明确的结论：**GitHub Pages 配置问题**。

但这里有一个**关键陷阱**：错误日志只是症状，不是根因。就像看到"发烧"不等于找到了"病毒"，看到部署失败不等于找到了配置问题。

## 第二章：根因分析的两种路径

![第二章：根因分析的两种路径](/images/illustrations/2026-02-22-github-pages-404故障排查深度分析与根因定位-03.png)


### 2.1 路径 A：症状层面分析（另一种模型的方案）

#### 分析方法

查看 GitHub Actions 失败日志 → 判断为 Pages 配置异常 → 建议用户手动修改 GitHub Settings

#### 诊断结论

> "尽管 `gh-pages` 已成功更新，站点仍返回 404。Pages 当前没有正确使用该发布产物（被关闭或分支/路径指向错误）。这是 GitHub Pages 配置层问题，而不是博客内容构建问题。"

#### 解决方案

修改 workflow 为 gh-pages 分支模式：

```yaml
# .github/workflows/hugo.yaml
jobs:
  deploy:
    uses: peaceiris/actions-gh-pages@v4  # 推送到 gh-pages 分支
    with:
      publish_branch: gh-pages
      force_orphan: true
```

#### 最终判断

**需要用户手动操作**：
> "建议的最终动作（用户侧）：在 GitHub 仓库页面确认 Pages 设置为：Source: Deploy from a branch, Branch: gh-pages, Folder: /(root)"

#### 问题所在

这个方案有两个致命缺陷：

1. **模式不匹配**：选择了 gh-pages 分支模式，但 GitHub Pages 设置是 "GitHub Actions"
2. **问题未解决**：即使执行了所有操作，404 问题依然存在
3. **甩锅给用户**：要求用户手动修改配置，增加了用户的操作成本

### 2.2 路径 B：根源层面分析（我的方案）

#### 分析方法

查看 GitHub Actions 失败日志 → **追溯 git 历史** → **查看 commit diff** → 识别配置错误 → 修复代码 → 自动解决

#### 关键步骤

**第一步：追溯 git 历史**

```bash
git log --oneline -10
```

输出：

```
6e4d588a Fix blog deployment mode and restore latest post assets/formats
91c88ce6 Update content
0a07fead Add 比安基恒等式 article and images
```

注意到 commit `6e4d588a` 的标题："Fix blog deployment mode"——这很可疑！

**第二步：查看 commit diff**

```bash
git show 6e4d588a --stat
```

关键发现：

```
 .github/workflows/hugo.yaml |  37 +++------
```

workflow 文件被大幅修改了！让我看看具体改了什么：

```bash
git diff 91c88ce6 6e4d588a -- .github/workflows/hugo.yaml
```

#### 根本原因定位

**之前的工作 workflow（正确）**：

```yaml
# GitHub Pages Infrastructure 模式
jobs:
  build:
    steps:
      - uses: actions/upload-pages-artifact@v3

  deploy:
    environment:
      name: github-pages
    uses: actions/deploy-pages@v4  # ✅ 正确
```

**被错误修改为**：

```yaml
# gh-pages 分支模式
jobs:
  deploy:
    uses: peaceiris/actions-gh-pages@v4  # ❌ 错误
    with:
      publish_branch: gh-pages
```

#### 核心发现

**GitHub Pages 有两种部署模式**：

1. **GitHub Pages Infrastructure**（正确）：
   - 使用 `actions/deploy-pages@v4`
   - 要求 GitHub Settings: Source → "GitHub Actions"

2. **gh-pages 分支模式**（错误）：
   - 使用 `peaceiris/actions-gh-pages@v4`
   - 要求 GitHub Settings: Source → "Deploy from a branch"

**Commit 6e4d588a 把正确的模式改成了错误的模式**，导致与 GitHub Settings 不匹配！

#### GitHub Pages 两种部署模式详解

> **GitHub Pages Infrastructure**：GitHub 官方提供的现代化部署架构，使用专门的 Pages 构建环境，通过 GitHub Actions 直接部署到 GitHub 的 Pages 基础设施。可以想象成走"官方通道"，直接将构建产物交给 GitHub Pages 团队管理的服务器。

> **gh-pages 分支模式**：传统部署方式，通过第三方 Action 将构建产物推送到专门的 `gh-pages` 分支，GitHub Pages 从该分支读取内容。可以想象成"快递模式"，先把东西打包送到指定地点，再由 GitHub Pages 去取。

**模式 1：GitHub Pages Infrastructure（推荐）**

**Workflow 配置**：
```yaml
name: Deploy Hugo site to GitHub Pages

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write      # 必需：授予 Pages 写权限
  id-token: write   # 必需：授予 OIDC Token 权限

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Hugo
        uses: peaceiris/actions-hugo@v3
        with:
          hugo-version: "latest"
          extended: true

      - name: Build with Hugo
        run: hugo --minify

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: ./public

  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

**GitHub Settings 配置**：
- Source: `GitHub Actions`
- （不需要选择分支，Actions 自动处理）

**优势**：
- ✅ **官方支持**：GitHub 官方维护，更新及时
- ✅ **安全性高**：使用 OIDC 认证，不需要 Personal Access Token
- ✅ **速度快**：直接部署到 Pages 基础设施，无需推送到分支
- ✅ **权限明确**：通过 `pages: write` 和 `id-token: write` 精确控制权限
- ✅ **环境隔离**：使用 `environment: github-pages`，支持部署预览

**劣势**：
- ⚠️ **配置稍复杂**：需要配置 permissions 和 environment
- ⚠️ **相对较新**：2022 年才推出，社区资料相对较少

---

**模式 2：gh-pages 分支模式（传统）**

**Workflow 配置**：
```yaml
name: Deploy Hugo site to gh-pages branch

on:
  push:
    branches: [main]

permissions:
  contents: write  # 必需：授予推送到分支的权限

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Hugo
        uses: peaceiris/actions-hugo@v3
        with:
          hugo-version: "latest"
          extended: true

      - name: Build with Hugo
        run: hugo --minify

      - name: Deploy to gh-pages branch
        uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./public
          publish_branch: gh-pages
          force_orphan: true
```

**GitHub Settings 配置**：
- Source: `Deploy from a branch`
- Branch: `gh-pages`
- Folder: `/(root)`

**优势**：
- ✅ **简单直观**：容易理解，就是推送到分支
- ✅ **成熟稳定**：使用多年，社区资料丰富
- ✅ **灵活性高**：可以手动修改 gh-pages 分支内容

**劣势**：
- ❌ **需要 GITHUB_TOKEN**：依赖 GitHub Token，存在安全风险
- ❌ **多一步操作**：需要推送到分支，再由 Pages 读取
- ❌ **仓库污染**：gh-pages 分支会出现在仓库列表中
- ❌ **非官方方式**：使用第三方 Action，维护依赖社区

---

#### 推荐做法

**基于您当前博客的配置，强烈推荐使用 GitHub Pages Infrastructure 模式**，原因如下：

1. **当前已正确配置**：
   - ✅ Workflow 已使用 `actions/deploy-pages@v4`
   - ✅ GitHub Settings 已设置为 `Source: GitHub Actions`
   - ✅ Permissions 和 Environment 已正确配置

2. **安全性更高**：
   - 无需存储和管理 Personal Access Token
   - 使用 OIDC 认证，自动管理凭证

3. **部署速度更快**：
   - 直接上传 artifact 并部署
   - 避免了 git push 到 gh-pages 分支的额外步骤

4. **更符合 GitHub 官方方向**：
   - GitHub 官方推荐的新方式
   - 持续得到官方支持和更新

**关键配置检查清单**：

```yaml
# .github/workflows/hugo.yaml 必须包含：
permissions:
  contents: read
  pages: write      # ✅ 必需
  id-token: write   # ✅ 必需

jobs:
  build:
    steps:
      - uses: actions/upload-pages-artifact@v3  # ✅ 必需

  deploy:
    environment:
      name: github-pages  # ✅ 必需
    uses: actions/deploy-pages@v4  # ✅ 必需
```

**GitHub Pages 设置检查**：
- 访问仓库 → Settings → Pages
- Source 应为：`GitHub Actions`
- （不应选择 `Deploy from a branch`）

#### 解决方案

**恢复正确的 workflow 配置**：

```yaml
name: Deploy Hugo site to GitHub Pages

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3

  deploy:
    environment:
      name: github-pages
    uses: actions/deploy-pages@v4
```

**触发重新部署**：

```bash
git commit --allow-empty -m "Trigger GitHub Actions deployment"
git push origin main
```

#### 问题自动解决

✅ 1-3 分钟后，GitHub Actions 自动完成部署
✅ 无需任何手动操作
✅ 博客恢复正常访问

### 3.2 思维模式对比

#### 线性思维 vs 系统性思维

**线性思维**（头痛医头）：

```
问题 → 症状 → 表面解决方案
  ↓     ↓        ↓
404  日志错误  gh-pages模式
```

**系统性思维**（根源治理）：

```
问题 → 历史分析 → 模式识别 → 代码修复
  ↓     ↓         ↓         ↓
404  commit  两种   恢复配置
     6e4...  模式
```

### 3.3 工具使用深度对比

| 工具 | 方法 A | 方法 B |

| `git log` | ❌ 未使用 | ✅ 查看最近 commits |

**关键差异**：

- 方法 A：只看了**错误日志**（症状）
- 方法 B：分析了**代码变更历史**（根因）

## 第五章：为什么会这样？

![第五章：为什么会这样？](/images/illustrations/2026-02-22-github-pages-404故障排查深度分析与根因定位-06.png)


### 5.1 认知偏差的影响

#### 表面现象的误导

GitHub Actions 失败日志很有"说服力"：

```
Failed to create deployment (status: 404)
Ensure GitHub Pages has been enabled
```

看到这个错误，很容易得出结论：**"Pages 配置有问题"**。

但这是一个**症状**，而不是**根因**。

#### 确认偏误

一旦接受了"Pages 配置有问题"这个结论，后续的所有诊断都会被这个偏见影响：

- 不会再深入检查代码变更历史
- 会优先寻找配置相关的解决方案
- 会倾向于让用户手动修复（因为"配置问题"通常需要手动操作）

### 5.2 深度分析的价值

#### Git 历史的真相

通过 `git log` 和 `git diff`，我们发现了**导致问题的时刻**：

```bash
# 之前（正确）
91c88ce6 Update content

# 之后（错误）
6e4d588a Fix blog deployment mode  # ← 引入问题！
```

这个 commit 标题"Fix blog deployment mode"本身就透露了问题——**它在尝试"修复"部署，但反而把配置改错了**。

#### 为什么 git 历史分析更重要？

**错误日志**告诉你是**什么失败了**：
```
Failed to create deployment (status: 404)
```

**git 历史**告诉你是**为什么失败**：
```
commit 6e4588a: workflow 从正确模式改为错误模式
```

**这就是"治标"与"治本"的区别**。

## 第六章：方法论总结

![第六章：方法论总结](/images/illustrations/2026-02-22-github-pages-404故障排查深度分析与根因定位-07.png)


### 6.1 核心原则

#### 原则 1：症状 ≠ 根因

错误信息只是症状，不是根本原因。必须追溯问题是如何被引入的。

#### 原则 2：历史很重要

当前的状态是历史变更的结果。要理解问题，必须看历史。

#### 原则 3：模式匹配

GitHub Pages 有两种部署模式，必须与 Settings 匹配。模式不匹配 = 404。

#### 原则 4：自动化 > 手动

能通过代码修复的问题，不要让用户手动操作。

### 6.2 调试方法论

#### 错误的调试路径（线性）

```
1. 查看错误信息
2. 搜索类似问题
3. 给出解决方案
4. 让用户执行
```

#### 正确的调试路径（系统化）

```
1. 查看错误信息
2. 分析 git 历史（找到引入问题的时刻）
3. 定位根本原因
4. 修复根本原因
5. 验证修复
```

### 6.3 工具使用策略

| 工具 | 用途 | 优先级 |
|------|------|--------|
| `git log` | 查看 commit 历史 | 🔴 高 |

## 第七章：启示与经验教训

![第七章：启示与经验教训](/images/illustrations/2026-02-22-github-pages-404故障排查深度分析与根因定位-08.png)


### 7.1 对 AI 模型的启示

#### 为什么有些模型会犯错？

1. **只看症状，不看根因**
   - GitHub Actions 失败日志只是表象
   - 代码变更历史才是根源

2. **缺少系统性知识**
   - 不知道 GitHub Pages 有两种部署模式
   - 不理解模式必须与 Settings 匹配

3. **手动修复思维**
   - 优先让用户手动操作
   - 而非通过代码自动化修复

#### 为什么我能解决？

1. **深度分析能力**
   - 不仅看症状，还看历史
   - 不仅看错误，还看引入错误的代码变更

2. **系统性知识**
   - 理解 GitHub Pages 的两种部署模式
   - 理解模式与 Settings 的对应关系

3. **自动化优先思维**
   - 通过代码修复而非手动操作
   - 让系统适应用户而非用户适应系统

### 7.2 对技术调试的启示

#### 经验教训

1. **不要相信表面现象**
   - 错误日志 ≠ 根本原因
   - 症状 ≠ 诊断

2. **追溯历史很重要**
   - 当前问题 = 历史变更的结果
   - 要解决问题，先看历史

3. **理解系统的两种模式**
   - GitHub Pages Infrastructure vs gh-pages 分支
   - 模式必须匹配 Settings

4. **自动化 > 手动**
   - 能用代码解决，不要让用户手动操作
   - 自动化修复成本低、效率高

### 8.1 Git Pre-commit Hook

为了防止类似问题再次发生，我创建了 Git pre-commit hook：

```bash
# .githooks/pre-commit
#!/bin/bash
echo "🔍 Running pre-commit checks..."

FILES=$(git diff --cached --name-only --diff-filter=ACM | grep '\.md$')

if [ -n "$FILES" ]; then
    python3 scripts/check_math_formulas.py $FILES
    if [ $? -ne 0 ]; then
        echo "❌ Math formula check failed!"
        exit 1
    fi
fi
```

**作用**：自动检查所有提交的 markdown 文件，阻止不符合规范的代码进入仓库。

## 结语：从症状到根源的跃迁

![结语：从症状到根源的跃迁](/images/illustrations/2026-02-22-github-pages-404故障排查深度分析与根因定位-10.png)


这次 404 故障的排查过程，完美地诠释了两种不同的思维模式：

**症状层面分析**（头痛医头）：
- 看到什么就是什么
- 针对表面现象给出解决方案
- 往往治标不治本

**根源层面分析**（系统治理）：
- 追溯历史，找到问题引入的时刻
- 理解系统的两种模式及其匹配关系
- 从根本上解决问题，防止复发

在技术调试中，**深度分析**比**表面观察**更重要。这不仅适用于 GitHub Pages 部署问题，也适用于各种复杂的系统故障：

> 🎯 **深度分析 > 表面观察**
> 🎯 **根源治理 > 症状缓解**
> 🎯 **自动化 > 手动操作**
> 🎯 **系统性 > 线性性**

这次故障排查的经验，将帮助我们在未来更快地定位和解决类似问题。同时，通过建立预防机制（如 Git pre-commit hook），可以从根本上减少这类问题的发生。

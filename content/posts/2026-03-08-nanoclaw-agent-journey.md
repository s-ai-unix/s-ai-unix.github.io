## 引子：当工具成为杠杆

![引子：当工具成为杠杆](/images/illustrations/2026-03-08-nanoclaw-agent-journey-01.png)


上个月读到胡渊鸣的那篇《我给 10 个 Claude Code 打工》，里面有一句话让我停下了滚动鼠标的手指：

> "我做事情的 ROI 变为了：我产出想法的速度，成为了唯一的瓶颈。"

这句话像一面镜子，照出了我过去三个月的真实状态。我一边在 NanoClaw 的泥潭里反复挣扎，一边看着别人用同样的工具实现 100 倍效率提升。同样的 Claude Code，同样的容器化 Agent 架构，为什么有人能同时驱动 10 个并行工作流，而我却在为"容器命名冲突"这种低级错误熬夜 debugging？

这不是一篇教程，而是一份踩坑记录。我想把过去三个月折腾 NanoClaw 的经历整理出来：15 个 bug、13 个小时的浪费，以及那些真正让我开始理解"给 AI 铺路"含义的瞬间。

## 第一部分：效率进化的核心洞察

![第一部分：效率进化的核心洞察](/images/illustrations/2026-03-08-nanoclaw-agent-journey-02.png)


在展开具体的踩坑记录之前，我想先分享经过这三个月折腾后形成的几个核心认知。这些认知可能比那些 bug 细节更有价值。

### 洞察一：从"效率幻觉"到"真实进化"

胡渊鸣在文章中提到："Vibe coding 给我提供了比原来手动写代码更快、更强 10 倍以上的正反馈，成瘾性很强。"

这句话道出了 AI 工具的双面性。初期使用 Agent 时，我确实体验到了这种"成瘾性"：想法可以瞬间转化为代码，需求可以快速得到响应，这种正反馈循环让人欲罢不能。

但很快我发现，这种快感背后隐藏着"效率幻觉"：

| 阶段 | 表象 | 实质 |
|------|------|------|
| ** honeymoon 期** | 花大量时间调 prompt、修配置 | 基础设施建设投入 |
| **平台期** | 验证 AI 输出、检查幻觉、反复澄清 | 质量控制成本 |
| **倦怠期** | 任务量反而增加，因为"反正 AI 能做" | 期望膨胀陷阱 |

真正的效率进化不是从 0 到 100 的直线上升，而是从 0 到 -20（学习成本），再到 50（初步熟练），最后才可能到达 100（系统成熟）。很多人在前两个阶段就放弃了。

### 洞察二："压榨 AI"与"AI 压榨我"的循环

胡渊鸣说："我压榨 AI，是因为我希望唯一的产能限制是我的思维；AI 压榨我，是因为 Vibe coding 给我提供了比原来手动写代码更快、更强 10 倍以上的正反馈，成瘾性很强。"

这段描述精准地刻画了我这段时间的状态。当 Agent 能 5 分钟完成以前 2 小时的任务时，你会不自觉地提高产出预期。以前是"一天完成一个任务"，现在变成了"一个小时内完成多个任务"。效率提升被新增的工作量对冲，最终结果是：绝对产出增加了，但单位产出的脑力消耗并没有减少。

打破这个循环的关键是：明确划定 Agent 的边界，而不是无限制地扩大它的使用范围。

### 洞察三：工具链的分层策略

经过三个月的探索，我逐渐形成了清晰的分层使用策略：

| 工具 | 使用场景 | 核心定位 |
|------|----------|----------|
| **OpenClaw（备用机）** | 轻量查询、快速验证、个人笔记整理 | 低摩擦入口 |
| **NanoClaw（主力环境）** | 生产级任务、复杂多步骤工作流 | 重型基础设施 |

这种分层让我的使用成本最优化：简单任务不浪费重型基础设施，复杂任务有可靠的隔离和状态管理。

一开始我还尝试了 NanoBot，它的模块化设计有不少亮点。但在实际使用中，我发现 NanoClaw 的容器隔离和状态管理更符合我的工作需求，所以最终形成了 OpenClaw + NanoClaw 的组合。

## 第二部分：实际落地的价值验证

![第二部分：实际落地的价值验证](/images/illustrations/2026-03-08-nanoclaw-agent-journey-03.png)


说了这么多认知层面的东西，具体落地时带来了什么价值？让我用四个实际案例来说明。

### 案例一：tic-expert Skill

这是我的核心工作场景。日常工作中需要处理大量技术文档和标准文件。每次面对技术咨询、标准解读、方案评估等需求，我需要快速定位相关条款、解释技术要求、生成分析报告。

tic-expert skill 整合了三部分知识源：

1. 本地知识库 `AI-Compliance-Expert-System`
2. Skills 目录下的标准条款拆解分析
3. Obsidian 中的工作笔记

实际使用场景：

> 用户问："我们的 DMS 系统（驾驶员监测系统）要满足哪些技术要求？"

以前的工作流：打开多个标准文档，搜索相关条款，查功能安全要求，查预期功能安全，整理成回复。耗时 2 到 3 小时。

现在的 Agent 工作流：@nanoclaw 群聊中发送问题，Agent 自动检索知识库，生成结构化回复，包含条款引用、检查清单、建议项目。耗时 5 分钟，质量更稳定。

**关键数据**：
- 响应时间：从 2-3 小时降至 5 分钟（36 倍提升）
- 条款覆盖率：人工检索容易遗漏跨标准关联，Agent 能自动映射
- 可复现性：同样的 query 得到一致的回复框架

### 案例二：news-aggregator Skill

AI 领域发展太快，每天需要跟踪 arXiv、Hugging Face、主流科技媒体的新闻。之前用 RSS 阅读器，但信息过载严重。

news-aggregator skill 每天定时执行：

1. 抓取指定源的更新
2. 用轻量级模型做摘要和分类
3. 生成一份 Markdown 简报，推送到指定群组
4. 重要论文自动触发 paper-interpreter 进行深度解读

这个 skill 本身不使用大模型（纯 Python + RSS），但依赖 NanoClaw 的容器调度能力保证隔离和定时执行。

**关键收益**：
- 信息覆盖率从 60% 提升到 95%
- 筛选时间从 45 分钟/天降至 2 分钟/天
- 重要论文不再遗漏

### 案例三：古籍研究 Agent

这属于个人兴趣项目。我构建了红楼梦的结构化知识库，包含人物关系、情节脉络、诗词赏析等。

Agent 能力包括：

* 人物关系查询："林黛玉和薛宝钗的初次见面是在哪一回？"
* 诗词检索："包含'花'和'月'的诗词有哪些？"
* 情节对比："对比宝玉和贾琏的情感线发展"
* 风格分析："这段文字体现了作者什么样的叙事技巧？"

这个案例的价值在于验证 Agent 在非技术领域的可迁移性。当知识库足够结构化，Agent 就能提供超越关键词检索的语义级分析。

### 案例四：paper-interpreter Skill

工作研究需要大量文献阅读。paper-interpreter 接收 PDF 或 arXiv 链接，执行以下流程：

1. 提取文本和图表（使用 pdffigures2）
2. 生成结构化摘要：研究问题、方法、结果、局限
3. 提取关键图表并嵌入 base64 编码的图像
4. 生成 HTML 格式的深度解读文档

一批 20 篇论文，人工阅读需要 2 到 3 天，Agent 批量处理只需几小时。当然，质量不如人工精读，但提供了有效的初筛能力，让我能把时间花在真正重要的论文上。

### 价值量化与效能提升

让我用数据说话：

| 任务类型 | 传统方式耗时 | Agent 辅助耗时 | 效率提升 | 质量稳定性 |
|----------|--------------|----------------|----------|------------|
| 标准条款检索 | 2-3 小时 | 5 分钟 | 24-36x | 更高（不遗漏条款） |
| 每日新闻筛选 | 45 分钟 | 2 分钟 | 22x | 中等（需人工复核） |
| 文学知识查询 | 15-30 分钟 | 1 分钟 | 15-30x | 高（结构化准确） |
| 文献初筛（20篇） | 2-3 天 | 2-3 小时 | 8-12x | 中等（需精读核心） |

**累计时间节省**：按每周 2 次标准咨询、每天新闻简报、每周 20 篇论文计算，每周节省约 15-20 小时。

但这些数字只说明了"效率"的一面，更重要的是"能力"的一面：

**tic-expert** 提供了以前难以实现的服务能力。没有 Agent 辅助，跨多个标准的复杂技术问题很难即时回答。这不是速度问题，是能力边界问题。

**news-aggregator** 让我保持对 AI 领域的全局感知。以前由于信息过载，我会有选择地放弃某些信息源；现在可以全覆盖，再由 Agent 做初步筛选。

**古籍 Agent** 展示了知识组织的全新方式。传统的读书笔记是线性的，Agent 让知识成为网状结构，任意节点都可以触发关联探索。

**paper-interpreter** 改变了我的阅读策略。以前是"每篇都读一点"，现在是"Agent 初筛 + 人工精读核心"，阅读深度反而提升了。

## 第三部分：效率进化的七个建议

![第三部分：效率进化的七个建议](/images/illustrations/2026-03-08-nanoclaw-agent-journey-04.png)


折腾了这么多，我开始理解胡渊鸣文章的核心观点。他的 10 个阶段不是炫技，而是一步步把"人类成为瓶颈"的部分移交给系统。对比他的方法论，我梳理出 7 个可以立即实施的优化建议。

### 1. 任务队列系统（Ralph Loop）

胡渊鸣提到的"Ralph Loop"是一个任务队列系统：人类只负责提需求（写任务描述），系统负责调度执行。

我目前的模式还是"单任务交互"：我提一个需求，等 Agent 完成，再提下一个。这种模式的问题：

* 上下文切换成本高
* 无法利用等待时间
* 没有任务状态的持久化

计划实现的任务队列：

```markdown
# PROGRESS.md

## 队列
- [ ] 任务1: 分析 ISO 42001 与 EU AI Act 的映射关系 | 优先级: P1 | 状态: pending
- [ ] 任务2: 更新 tic-expert 的 SOTIF 知识库 | 优先级: P2 | 状态: pending

## 进行中
- [x] 任务3: 修复 news-aggregator 的 RSS 源 | 开始: 2026-03-08 | 状态: running

## 已完成
- [x] 任务4: 优化 paper-interpreter 的图表提取 | 完成: 2026-03-07 | 耗时: 2h
```

Agent 自动读取 PROGRESS.md，按优先级执行，人类只 review 结果和补充新任务。

### 2. 双文件记忆系统

胡渊鸣使用 `CLAUDE.md` + `PROGRESS.md` 的组合。我目前只有 `CLAUDE.md`（项目上下文），缺少 `PROGRESS.md`（执行状态）。

`CLAUDE.md` 的内容：

* 项目背景和长期目标
* 技术栈和关键文件路径
* 用户画像和偏好
* 已验证的最佳实践

`PROGRESS.md` 的内容：

* 当前任务队列
* 进行中任务的上下文
* 已完成任务的总结和经验
* 遇到的问题和解决方案

两者的区别在于时间维度：`CLAUDE.md` 是静态知识，`PROGRESS.md` 是动态状态。有了后者，Agent 可以真正"记住"上次做到哪里，而不是每次重新加载上下文。

### 3. 高权限沙箱（--dangerously-skip-permissions）

这是最反直觉的一点。为了安全，Claude Code 默认有很多权限确认。但在可控的容器沙箱内，这些确认反而成为效率瓶颈。

胡渊鸣的建议：在容器内使用 `--dangerously-skip-permissions`，让 Agent 拥有完整执行能力，同时通过容器隔离保证安全。

我的实践：

```bash
# 容器内启动 Claude Code
claude --dangerously-skip-permissions
```

前提是容器文件系统与主机隔离，即使 Agent "失控"，破坏范围也限于容器内。这需要配合 `--rm` 自动清理和只读挂载敏感目录。

### 4. 零确认规则（Auto-Execute 边界）

明确划定哪些操作不需要确认：

| 类型 | 示例 | 确认策略 |
|------|------|----------|
| 文件读取 | 读代码、读配置 | 零确认 |
| 构建命令 | npm run build, make | 零确认 |
| 测试运行 | npm test, pytest | 零确认 |
| 单文件编辑 | 修改一个函数 | 零确认 |
| 多文件重构 | 跨模块改动 | 单次确认 |
| 破坏性操作 | rm, git reset | 必须确认 |
| 网络请求 | curl, fetch | 必须确认 |

关键是把"确认"作为稀缺资源，用在真正需要人类判断的地方。

### 5. Git Worktree 并行

胡渊鸣用 Git Worktree 实现多分支并行开发。我的场景是：主分支跑稳定版本，worktree 跑实验性改动，互不干扰。

```bash
# 创建 worktree
git worktree add ../nanoclaw-experiment feature/new-scheduler

# 两个目录可以独立运行
cd ~/git/Agents/NanoClaw && npm run dev
cd ~/git/Agents/nanoclaw-experiment && npm run dev
```

这样可以在不停止主服务的情况下，测试新功能或复现 bug。

### 6. 语音输入集成

胡渊鸣提到用语音输入提需求，把自然语言的模糊性转化为优势。我目前的输入还是以文字为主，但已经开始尝试：

* 用语音快速记录任务想法，转文字后让 Agent 整理成 PROGRESS.md 格式
* 用语音描述复杂需求，Agent 转换为结构化的技术规格

关键不是语音本身，而是降低"提出想法"的摩擦成本。当表达速度接近思考速度时，创意才不会被工具打断。

### 7. 从"验证代码"转向"验证目标"

这是我最大的心态转变。以前我的关注点是"代码对不对"：检查每一行修改，验证语法正确性，review 变量命名。

现在的关注点是"目标达没达成"：Agent 给出的方案是否解决了问题，边界情况是否覆盖，性能是否可接受。

具体实践：

* 要求 Agent 提供测试用例，而非逐行解释代码
* 要求 Agent 提供 diff 对比，而非口头描述改动
* 要求 Agent 说明回滚方案，而非只讲正向流程

这种转变的本质是信任层级的提升：从"我不相信你的代码"到"我相信你的能力，但我需要验证结果"。

## 第四部分：NanoClaw 折腾实录

![第四部分：NanoClaw 折腾实录](/images/illustrations/2026-03-08-nanoclaw-agent-journey-05.png)


前面的内容展示了价值和方法，现在轮到血泪史了。三个月下来，我记录了 15 个实质性问题，总计浪费 11 到 13 小时。

### 为什么选择 NanoClaw

先交代背景。日常工作中需要处理大量技术文档和标准文件。

选择 NanoClaw 的逻辑是：涉及敏感数据和复杂知识库，隔离性和可扩展性是硬需求。这个判断没有错，但我低估了"高可控性"背后的维护成本。

### 15 个 Bug 的分类解剖

**配置类（5 个）**

| Bug | 症状 | 根因 | 浪费时长 |
|-----|------|------|----------|
| 数据库路径混淆 | 检查 `nanoclaw.db` 发现是空的 | 实际数据在 `store/messages.db` | 45min |
| iCloud vs 本地路径 | Obsidian 笔记找不到 | 混用 iCloud 路径和本地路径 | 30min |
| Allowlist 覆盖数据库 | 配置的挂载点丢失 | 同步函数逻辑错误，覆盖而非合并 | 1.5h |
| 路径扩展错误 | 路径缺少用户目录前缀 | 环境变量解析问题 | 40min |
| JSON 格式兼容性 | Apple Container 切换失败 | 配置字段类型不匹配 | 1h |

**运行时类（6 个）**

| Bug | 症状 | 根因 | 浪费时长 |
|-----|------|------|----------|
| Docker Desktop 假启动 | 容器命令无响应 | Desktop 界面开着，但引擎没启动 | 20min |
| 容器命名冲突 | "container already exists" | 手动改成固定命名，时间戳被去掉 | 2h |
| 多进程冲突 | Telegram 409 Conflict | launchd 自动重启 + 手动启动冲突 | 1.5h |
| ANTHROPIC_BASE_URL 缺失 | API 认证失败 | 容器内环境变量未传递 | 1h |
| Session 文件累积 | ENFILE: file table overflow | 每次运行复制 skills，23,187 个文件，587MB | 3h |
| Telegram getUpdates 冲突 | "terminated by other getUpdates request" | 多个实例抢 webhook | 1h |

**验证类（4 个）**

| Bug | 症状 | 根因 | 浪费时长 |
|-----|------|------|----------|
| 修改后不验证生效 | 代码逻辑没变化 | 旧进程还在跑，新代码没加载 | 1.5h |
| Build 成功但运行失败 | TypeScript 编译通过，运行报错 | 类型检查通过，运行时依赖缺失 | 40min |
| 容器启动成功但技能缺失 | Agent 不响应自定义指令 | Skills 复制路径错误 | 30min |
| 日志滚动过快 | 关键错误被冲掉 | 未配置日志级别和切割 | 20min |

### 最痛的三个教训

**教训一：Session 文件累积导致的 ENFILE 灾难**

这是耗时最长的一个 issue。NanoClaw 的设计是每次消息触发创建一个新容器，容器内需要加载 Skills。最初的实现是把 skills 复制到 `data/sessions/{group}/.claude/skills/`，以保证隔离性。运行几周后，我开始遇到奇怪的报错：

```
Error: ENFILE: file table overflow, copyfile ...
```

查了一下，ENFILE 表示系统文件描述符表已满。进一步检查发现，Session 目录下有 23,187 个文件，占用 587MB。每个容器复制一份 skills，累积起来成了灾难。

解决方案是改用符号链接而非复制，或者定期清理。但这个问题的发现花了 3 小时，因为我一开始以为是系统配置问题，调高了 ulimit，结果只是延缓了崩溃。

**教训二：试图"改进"已经工作的设计**

容器命名逻辑原本是这样的：

```typescript
const containerName = `nanoclaw-${safeName}-${Date.now()}`;
```

每次唯一命名，配合 `--rm` 自动清理，无冲突风险。我觉得这样"太乱"，改成固定命名：

```typescript
const containerName = `nanoclaw-${safeName}`;
```

意图是方便手动检查容器状态。结果在高并发场景下（快速多条消息），第二次消息到达时第一次的容器还没销毁，直接报 "container already exists"。

这个改动花了 2 小时回滚和验证。核心教训：不要基于美学偏好修改工程代码，尤其是并发相关的逻辑。

**教训三：多进程冲突的 409 噩梦**

Telegram Bot 使用 long polling 接收消息。NanoClaw 通过 launchd 管理进程，配置中 `KeepAlive` 设为 true。某次调试时我手动启动了一个实例，launchd 又自动拉起一个，两个进程同时调用 `getUpdates`，Telegram 服务器返回：

```json
{"error": "Conflict: terminated by other getUpdates request"}
```

更糟的是，两个进程互相抢占，导致服务完全不可用。花了 1.5 小时才定位到是双进程问题，而不是代码 bug。

现在的 launchd 配置明确设置了 `KeepAlive: false`，启动前强制检查：

```bash
ps aux | grep nanoclaw
```

### 备用机同步困境

折腾 NanoClaw 的同时，我也在备用机上部署 OpenClaw 作为对比。

OpenClaw 在备用机上的部署确实轻松，几分钟就能跑起来。但当你试图同步两台机器的工作状态时，痛苦开始了。OpenClaw 的配置分散在多个文件中，没有统一的状态管理，导致配置漂移几乎不可避免。我在主机器上修复的 allowlist 问题，备用机上又重现一遍；主机器积累的技能优化，备用机完全不知情。

NanoClaw 试图用数据库存储状态解决这个问题，但代价是备份和迁移的复杂度。我最终写了一个同步脚本，通过 rsync 定时同步 `store/` 目录和 `.env` 配置。这个方案不够优雅，但有效。

这段经历让我意识到：**工具选择本质上是在"简单但受限"和"复杂但灵活"之间做权衡**。OpenClaw 的简单让你快速开始，但也快速触及天花板；NanoClaw 的灵活让你能实现复杂场景，但需要投入大量时间在基础设施上。

回头看，如果重新选择，我可能会在备用机上继续使用 OpenClaw 做轻量任务，主机器用 NanoClaw 承接核心工作流，而不是试图让两者完全同步。这种"分层架构"可能是更务实的方案。

## 结语：给 AI 铺路

![结语：给 AI 铺路](/images/illustrations/2026-03-08-nanoclaw-agent-journey-06.png)


回到胡渊鸣的那句话："我做事情的 ROI 变为了：我产出想法的速度，成为了唯一的瓶颈。"

三个月的折腾让我明白，这句话有一个前提：你必须先建好路。Agent 不是魔法，它不会自动理解你的业务场景、你的知识库结构、你的质量标准。在达到"想法即产出"的状态之前，你需要投入大量时间做基础设施建设：

* 搭建知识库和 RAG 系统
* 设计 Agent 能理解和使用的工具
* 建立反馈循环，让 Agent 从错误中学习
* 编写文档，把隐性知识显性化

这 15 个 bug、这 13 个小时的浪费，大部分发生在"铺路"阶段。当你看到有人用 AI 实现 100 倍效率时，不要忽略他们背后投入的基础设施成本。

对于同在技术领域的读者，我的建议是：

1. **先跑通一个案例**：不要试图一步到位搭建完整系统，先让一个具体任务（如"查询 EU AI Act 条款"）跑通
2. **投资于上下文**：Agent 的表现取决于你提供的上下文质量，花时间编写高质量的 CLAUDE.md 和技能文档
3. **建立信任边界**：明确哪些可以自动化，哪些必须人工确认，不要让 Agent 在关键决策上"猜测"
4. **记录和复盘**：每次故障都是改进的机会，建立 bug 日志和经验总结机制

工具只是杠杆。当杠杆足够长，支点的微小差异会被放大。NanoClaw 给了我一个足够长的杠杆，而我正在学习如何找到正确的支点。

胡渊鸣文章的最后说："2026 年，任何一个人类学英语的速度，都赶不上 AI 中英文翻译能力提升的速度。"

我想补充一句：但人类定义问题、判断价值、建立信任的能力，短期内还无法被替代。Agent 时代的核心竞争力，是"给 AI 铺路"的能力。铺好路，然后让 AI 跑起来。
